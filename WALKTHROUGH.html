Finominal Optimizer Walkthrough

A REST API that takes a portfolio and returns a better one, under five different definitions of “better”. Here is how it works, what was decided, and what was left undone.

  • 773 lines of Python
  • 5 strategies
  • 5 funds, 1993–2026
  • deps: fastapi · pandas · numpy · scipy

The approach

One matrix in, one weight vector out

Every strategy in this codebase reduces to the same signature. Given a matrix of daily returns — one row per trading day, one column per fund — produce a vector of weights that sums to 1. 

def some_strategy(returns, bounds, request) -> np.ndarray:
    # returns: (5413 days, 3 funds), each cell a fraction
    ...
    return weights   # length 3, non-negative, sums to 1.0

Four of the five then differ in exactly one thing: the objective function they hand to the solver. That uniformity is the design. Adding a strategy means writing one lambda, not touching the API, the schemas, or the data layer.

The other half of the approach is the measurement window, which is not a parameter. It is derived from the holdings — the longest stretch over which all of them have data. Ask for SPY and AGG and you measure from 2003; add IEFA and the window starts in 2012 and every resulting number changes. SPY's CAGR reads 10.89% over its own history and 15.02% over the five-fund window. Same fund, same data.

Decision

The window is a consequence of the request, not an input to it. This makes every figure in a single response mutually comparable, and it matches the reference API: its example sends start_date: "2004-11-18", which is exactly the inception date of the latest-starting fund in its own holdings list. Our request carries no date range at all, since nothing could honour one.

How the API works

The life of a request

One endpoint, POST /. Six stages, each able to reject with a specific status rather than failing deep inside numpy.

  1. Validate the payload. Pydantic checks types and ranges, then two model-level rules: weights must sum to 1.0 within 1e-9, and no ticker may appear twice. utils/schemas.py
  2. Resolve the window. Load the return matrix, keep only dates where every requested ticker traded, reject an unknown ticker with 400 and too little overlap with 422. utils/market_data.py → common_window()
  3. Assert column order. The weights are positional; if the matrix columns ever stopped matching the requested holdings, every number would be silently wrong rather than failing. utils/optimizer.py → optimize()
  4. Dispatch the strategy. A dict keyed by the enum. An import-time assertion fails loudly if an objective is advertised with no implementation behind it. utils/optimizer.py → STRATEGIES
  5. Solve. Closed form for equal weights; SLSQP for the rest, always with an equality constraint pinning the weights to 1. utils/optimizer.py → _solve()
  6. Assemble the response. Zip holdings against weights, round to four decimals, report current, optimized, and the change. utils/optimizer.py → optimize()

The response

Deliberately thin. An earlier version returned per-holding metrics, portfolio before-and-after figures, and the window used. All of it was cut.

Trade-off

The window that produced these weights is neither settable nor reported. It is deterministic — the same holdings always give the same window — but a caller cannot see that adding a fund silently shortened their measurement period from 21 years to 13.

The five strategies

Each one is an objective function

SLSQP minimizes, so maximizing Sharpe means handing it the negative. The differences between strategies fit in a table.

StrategyObjectiveNeeds
equal_weighted np.full(n, 1/n) nothing
min_volatility w @ cov @ w covariance
risk_parity ((shares(w) - 1/n) ** 2).sum() covariance
min_drawdown max_drawdown(returns @ w) full return path
sharpe_ratio -(w @ mu) / sqrt(w @ cov @ w) covariance, means, yields

Run against AGG / GLD / SPY over their shared 21.52 years, each wins its own objective and loses the others. That mutual exclusivity is the best available correctness signal: a swapped or mis-signed objective would break it immediately.

Why min_drawdown is the awkward one

Four strategies read a 3×3 covariance matrix. Drawdown cannot: it depends on the order of returns, not their distribution. Shuffle SPY's daily returns and CAGR, volatility and total return are all identical; drawdown swings between 38% and 54%. So the objective compounds a 5,413-row equity curve on every evaluation, 235 times per solve: 31 ms against 1.3 ms for min_volatility, roughly 23×.

It is also not smooth, which means a gradient solver carries no theoretical guarantee. Rather than assume, I compared it against differential_evolution, a global optimizer, across 2-, 3-, 4- and 5-holding requests. Gaps ranged from 0.0000% to 0.0050%, and eight random starting points converged to the same point.

Trade-off

That verification holds for this data set, not in general. If the funds change materially the comparison needs re-running, and a global optimizer or multi-start may become necessary. The check is documented rather than automated.

Decisions

The choices that shaped the code

Fractions everywhere, no percentages

0.3 means 30%; min_dividend_yield: 0.025 means 2.5%. The reference API mixes conventions — fractional weights alongside a yield expressed as 2.5. One rule for the whole payload removes a class of 100× error, at the cost of the reference's own payloads needing one field converted.

Two strategies ignore weight bounds, on purpose

Decision

equal_weighted and risk_parity accept min_weight and max_weight, validate them, and discard them. Box constraints contradict what those strategies mean: an equal split is equal, and equal risk contribution is equal. Clamping either would break the property that defines it. The other three apply bounds.

Bounds are clamped after solving — except once

min_volatility and min_drawdown solve unconstrained, then pin out-of-range weights to the bound they breached and redistribute the difference so the book still totals 100%. sharpe_ratio passes its bounds straight to the solver instead.

Decision

The asymmetry is deliberate. sharpe_ratio can also carry a dividend-yield floor, and clamping weights after the solve could drag the yield back below that floor — returning a result that quietly violates the request. Any strategy that gains a portfolio-level constraint needs the same treatment.

Infeasibility is detected before the solver runs

Minimums summing above 1, maximums summing below it, or a yield floor no allocation can reach are each rejected with 422 and a specific message. The yield ceiling accounts for caps: across AGG / GLD / SPY it is 3.97% unbounded, but a 50% cap on every holding drops it to 2.48%. It is computed by seating each holding at its floor then filling from highest yield down, which is exact for a linear objective under box and sum constraints. Left to SLSQP these surface as an opaque convergence failure.

metrics.py was cut down to two functions

Instrumenting a live request showed that of nine functions, only max_drawdown was ever called. The rest described a portfolio rather than optimizing one, and the maths the solver needs is written inline where it can be differentiated. They were deleted; the module went from 131 lines to 38.

Trade-off

There is now no way to measure an allocation from the codebase — no CAGR, volatility or Sharpe function exists. Every figure in this document was produced by inline numpy, which the strategy documentation records but the code does not.

Shortcuts

What was left undone

Three items in the specification are not implemented, and one earlier wart has since been fixed. None is hidden behind a stub that pretends otherwise.

Shortcut · not implemented

Factor betas, the specification's bonus item. Data.xlsx - Factor Returns.csv sits in data/ and is referenced by zero lines of code. Momentum, Size and Value are present; Quality and Volatility, which the reference response also reports, are not in the data at all — and the reference returns 0 for exactly those two.

Shortcut · partial

Portfolio-level constraints. One of five is implemented. min_dividend_yield works as a real inequality constraint inside the solver. min_cagr, max_volatility, max_drawdown and a volatility range are accepted in the payload and silently dropped by pydantic. The specification asks for them to be respected where feasible.

Decision · resolved

The inert date fields were removed. start_date, end_date, country_code and rebalance_frequency were declared on the request and ignored by the optimizer — a field that looks like it filters and does not is worse than no field. The request is now three keys: holdings, optimization_objective, and an optional min_dividend_yield. Pydantic drops unrecognised keys, so payloads written for the reference API still work unchanged; they simply no longer imply the caller controls a window they cannot.

Shortcut · no test suite

There are no automated tests. A pytest suite of 117 cases was written and then rolled back at the client's request. What remains is six markdown files in tests/, each holding a request and the response it should produce, verified by hand against the running API. They document behaviour but nothing runs them.

Two smaller ones worth naming

  • Rounding can make a tight constraint look violated. The solver satisfies a 2.5% yield floor exactly; recomputing from weights rounded to four decimals gives 2.49989%, short by 1.1 parts per million. A validator applying a strict >= to the response would flag it.
  • The risk-free rate is 0, so Sharpe is return-per-unit-risk rather than a true excess-return Sharpe. The data contains no cash series to derive a real rate from. Matching the reference's figures would imply roughly 2.65%.

Two documents sit alongside the code. README.md covers setup, the endpoint contract and the conventions. STRATEGIES.md explains the maths as runnable code — every example in it was executed to confirm it produces the output shown.
